# Phase 0 Research: Noren MVP

Date: 2026-10-29. All external evidence is in `research/01` to `research/07`; two fresh lookups were made during planning (Clerk docs through Context7; AI SDK docs at ai-sdk.dev). No NEEDS CLARIFICATION remain. Items that cannot be confirmed from a primary source yet are listed as verify-at-build (V1 to V8) rather than assumed.

## D1. Framework and hosting
- **Decision**: Next.js 16 (App Router) on Vercel, Node.js 24, single project.
- **Rationale**: One deploy for pages, route handlers and cron; Marketplace integrations for auth, database and storage provision environment variables automatically; matches the owner's tooling.
- **Alternatives**: Self-hosted container (more setup now; stays possible later because data access and storage sit behind interfaces); a separate API service (unneeded at pilot scale).

## D2. Accounts, roles and invite-only sign-up
- **Decision**: Clerk (owner's choice) proves who a person is; Convex decides what they may do (D19). Set Access mode to Invite-only and activate Clerk's Convex integration, so Convex validates the Clerk token against the Frontend API URL. Stewards create invitations through the Backend API, and an invitation carries no role. The role (`user`, `creator`, `business_owner`, `steward`) lives only in the Convex `person` row, found through the Clerk user ID in the verified token (`identity.subject`). A new person starts as `user`, a steward sets the role, and the first steward is created once with an admin-only `npx convex run` command. Every Convex function checks the role itself, so no route handler can forget to.
- **Evidence (verified in Clerk docs)**: Invite-only mode lets users be added by invitations, enterprise connections or manual creation, and the sign-up component is available only with a valid invitation link. `invitations.createInvitation` accepts `emailAddress`, `redirectUrl` and `publicMetadata` and is rate limited to 100 requests per hour. The basic-RBAC guide stores the role in `publicMetadata`, adds it to the session token, and reads `sessionClaims.metadata.role` on the server.
- **Rationale**: Delivers FR-020 and FR-021 with almost no custom code. Roles are never trusted from the client.
- **Alternatives**: Auth0 or Descope (more setup or fit-for-purpose gaps), own accounts (too slow). Lock-in is mitigated by the `person` mirror and one `requireRole` helper.
- **Evidence for the Convex link** (docs.convex.dev/auth/clerk): activate the Convex integration in the Clerk dashboard, set `CLERK_JWT_ISSUER_DOMAIN` (the Clerk Frontend API URL) on the Convex deployment, declare it in `convex/auth.config.ts` with `applicationID: "convex"`, and read the caller with `ctx.auth.getUserIdentity()`. The docs say the production Frontend API URL looks like `https://clerk.<your-domain>.com`, which agrees with the earlier finding that a production Clerk instance needs a domain you own.
- **Instance: production from the start (owner's decision, 2026-10-29)**: the owner will skip a development-only phase and run Clerk as a production instance. Verified in Clerk's docs: (a) production needs a domain you own and DNS records on it (guides/development/deployment/production); (b) on that page, SSO connections, Integrations and Paths settings do not copy over from development, so the Convex integration is activated again and every setting is checked on the production instance; (c) `pk_live_` and `sk_live_` keys are refused on `localhost` with "Production Keys are only allowed for domain ...", and the one workaround (a hosts-file subdomain of the production domain served over HTTPS on port 443) is "strongly discouraged and not officially supported" (guides/development/troubleshooting/using-production-keys-in-development). Consequences: the production keys belong in the Vercel Production environment variables, not in `.env.local` for `pnpm dev`; the Frontend API URL becomes `https://clerk.<domain>` and is set as `CLERK_JWT_ISSUER_DOMAIN` on the Convex production deployment; the users and settings of the development instance do not carry over. **Decided 2026-10-30**: the domain is `noren.yooi.me` (DNS at Spaceship; no records for it yet). The owner first chose to keep the development instance for local sign-in, then reversed it the same day: one production instance for everything, because users cannot be moved between Clerk instances. **Revised 2026-10-30 (later)**: the owner dropped the `dev.noren.yooi.me` workaround (a subdomain pointing at the development machine's Tailscale address), because that machine is remote, highly secured and strict, and nothing should be routed to it. Sign-in is therefore tried only on the deployed site at `https://noren.yooi.me`. Locally, logic is covered by tests that need no Clerk (`convex-test` and Vitest); `pnpm dev` is for looking at pages. Both Convex deployments (dev `brazen-gull-39` and production) trust the one production issuer, and each gets its first steward from its own `bootstrapSteward` run. Consequence: the first real sign-in (T016 V3) waits for the Convex production deployment and the first Vercel deploy (T008). The development instance `enabled-bear-1943` and its test user are retired.
- **Verify (V1)**: Where Clerk processes account data, for the privacy notice (not verified). The earlier idea of copying a role from invitation metadata into the session token is dropped (D19).

## D3. Database and access layer
- **Decision**: Convex (the owner's existing stack, D19) for all data and server functions. The schema is `convex/schema.ts` with validators. Every write goes through one `mutation` wrapper built with `convex-helpers` Triggers, so the cross-document rules in `data-model.md` run inside the same transaction and abort the write when broken; an ESLint rule forbids importing the raw `mutation`. Plain `lat` and `lng` fields with an index; at tens of places a bounding-box lookup is an index range on latitude filtered by longitude. No vector search in the MVP.
- **Evidence**: Convex docs: every mutation is a transaction, all reads and writes atomic and isolated, retried automatically on conflict. `convex-helpers` README: triggers run atomically with the write, and a thrown error aborts it. `convex-test` runs functions against a mock backend, so the rules are tested without a deployment.
- **Rationale**: One vendor already in use, official Clerk integration, no connection or driver choices, and typed functions end to end. Convex has no CHECK constraints, foreign keys or unique indexes, so those rules move into code: uniqueness (`place.slug` per region, `pin.place_id`, `person.clerk_user_id`) is an indexed read before the insert inside the same mutation, which is safe because transactions are serialisable.
- **Alternatives**: Neon Postgres with Drizzle (the first draft of this plan; rules were database triggers and constraints, now superseded, D19); Supabase or Turso.
- **Limit to respect**: one commit-time rule has no direct Convex equivalent: "a page sentence that is not held cites at least one claim". Sentences and their citations are written together by a single mutation, and publishing a page version re-checks every sentence.
- **Verify (V3)**: Triggers fire on every write path the app uses (`insert`, `patch`, `replace`, `delete`); the invariant tests pass in `convex-test`.

## D4. Interview audio
- **Decision**: Convex file storage behind the `Storage` port. A mutation that checks the caller and the interview's consent issues a short-lived upload URL (valid one hour, per the docs); playback and processing read the file inside Convex or through an authenticated route; `ctx.storage.delete` removes it when consent is withdrawn. The default retention is provisional: delete after the transcript is corrected and claims are confirmed, because the retention question is deferred to the second clarify.
- **Evidence** (docs.convex.dev/file-storage): file size is not limited, but the upload POST has a two-minute timeout. A 30-minute speech recording at about 32 kbps Opus is roughly 7 MB, which a normal mobile connection sends well inside two minutes; the browser recorder is configured for that bitrate and retries on failure.
- **Rationale**: Voice is personal data (research/06); one vendor and one access check cover the files and the interview they belong to.
- **Alternatives**: Vercel Blob private store with resumable uploads (the first draft; worth switching back to if long phone recordings hit the two-minute limit, which is why the port stays), S3 (more setup).

## D5. Map and place search
- **Decision**: MapLibre GL JS with OpenFreeMap tiles; Nominatim through a server proxy with caching, search on submit only (autocomplete is forbidden by its policy); the person-placed pin is the truth. The public demo needs no live search because seed places are pre-pinned.
- **Evidence**: research/01 (licences, policies, Japanese tests, glyph caveat). Protomaps fonts lack CJK glyphs, so labels use hosted glyphs or `localIdeographFontFamily`.
- **Alternatives**: Google, Apple or Mapbox (storage and per-fork account terms), Photon (public server returned no Japanese in tests). Self-host Nominatim or Protomaps before real traffic.
- **Verify (V5)**: Japanese labels render correctly for Nagasaki in the chosen style.
- **Outcome (V5, T050, 2026-10-30)**: Verified in a real Chromium on the production build, OpenFreeMap "liberty" style at the Nagasaki default centre (zoom 10): 長崎市, 諫早市 and 五島灘 draw in Japanese beside their Latin names, with no missing-glyph boxes, and the OpenStreetMap and OpenFreeMap credits show under the map. Limit of this check: it covers city and sea labels at one zoom, not street or shop labels; recheck at a street zoom once real places are pinned.

## D6. Source embeds and liveness
- **Decision**: Adapters match a URL pattern and produce embed markup that we generate ourselves from the validated URL (Meta embed blockquote and script, YouTube no-cookie iframe, X blockquote and widgets script, TikTok Embed Player iframe), never injecting arbitrary HTML returned by a remote service. Google Maps URLs store the `place_id` and link out. Anything else becomes a link card with a user-typed title. We store only URL, platform, author link, date and the creator's note. A daily cron checks sources where a public signal exists and hides gone entries; stewards can also mark a source gone.
- **Evidence**: research/03 and 04 (display-only terms, tokenless Meta oEmbed since mid-2026, 1,000 requests per hour cap, TikTok oEmbed deprecation notice, Meta author and thumbnail fields removed).
- **Alternatives**: Calling oEmbed and injecting the returned HTML (XSS and terms risk), scraping (excluded).
- **Verify (V4)**: How deleted posts show up for Meta embeds.

## D7. AI language work and grounding
- **Decision**: AI SDK with language models addressed through AI Gateway `provider/model` strings. Model IDs are fetched from the gateway at build time, never taken from memory. Claim extraction uses schema-constrained output (the gateway docs confirm structured output for language models) with a required quote span. A grounding gate runs deterministic checks (claim IDs exist, quote is a substring of the source span, no sentence without an ID) and then an entailment check by a model from a different vendor; any failure holds the sentence for human review. Model versions go in the audit log. Citations and structured output are not mixed (research/05).
- **Rationale**: Enforces Principle V mechanically and measures SC-003.
- **Alternatives**: One vendor for both generation and checking (shared blind spots), free-form prompts (no guarantees).
- **Verify (V7)**: Current model list, schema output behaviour, and the second-vendor check.

## D8. Transcription and translation
- **Decision**: `Transcriber` interface implemented with the AI SDK `transcribe` function and one direct provider package, chosen by a short bake-off on a Japanese mock recording that contains a place name. The AI SDK docs list OpenAI, ElevenLabs, Groq, Mistral, Azure, Deepgram, AssemblyAI and Google among transcription providers, return text, segment times, language and duration, and do not document speaker labels. The AI Gateway docs list no transcription models, so the gateway is not used for this step. Speakers are marked in the correction screen, not by the model. OpenAI's whisper-1 and gpt-4o-transcribe are retiring on 2027-02-26 (research/05) and are not candidates. Translation runs through a language model with a place-name glossary, only on inputs constitution V allows: owner-confirmed claims, notes and replies a contributor typed, and (for live captions) chunks of an interview whose consent covers AI processing. It is labelled machine translation until a person confirms it. DeepL's free plan is excluded because it forbids personal data (research/05). Live captions are out of the MVP; near-live can later reuse `transcribe` on short chunks.
- **Rationale**: The demo audio is a consenting team member's mock interview, so cross-border transfer does not block the MVP; the choice still matters for the pilot.
- **Verify (V2)**: Bake-off result and where each candidate processes audio.

## D9. Internationalisation
- **Decision**: A `[lang]` route segment with typed Japanese and English dictionaries, following the Next.js internationalisation guide, with locales read from the region config. No extra library.
- **Rationale**: Two languages and a small interface do not justify a dependency.

## D10. UI and accessibility
- **Decision**: Tailwind CSS with shadcn/ui components (Radix primitives). Every page has a list view next to the map, full keyboard use, and text alternatives. Target WCAG 2.2 AA, checked with axe in the end-to-end tests.
- **Rationale**: Delivers FR-028 without custom widgets.

## D11. Public demo and indexing
- **Decision**: Each place has a visibility: `draft` (stewards, the verified owner and the creator who made the place), `demo_public` (anyone, read-only), `pilot` (signed-in users, later). The public demo serves only `demo_public` places whose content is mock, openly licensed, or posts from creators who agreed. `proxy.ts` adds `X-Robots-Tag: noindex, nofollow` to every response and `robots.txt` disallows everything. A short Japanese and English notice explains that pages load third-party embeds.
- **Rationale**: Implements FR-021 and FR-029 and the constitution's launch-gate rule.
- **Verify (V8)**: The notice wording is reviewed (research/06 flags a notice duty under Japan's Telecommunications Business Act).

## D12. Link counting
- **Decision**: First-party redirect `/out/[sourceId]` increments a per-day aggregate counter and returns a temporary redirect. No IP address or cookie is stored; obvious bots and prefetch requests are skipped; mock activity is tagged and excluded.
- **Rationale**: Delivers FR-024 with minimal data (research/06).

## D13. Testing
- **Decision**: Vitest for adapters' URL matching, the claim state machine, the grounding gate and the authorisation matrix; contract tests that run each port's implementation against the same suite; Playwright for user stories 1 to 5, 7 and 9 with axe. Test data uses mock users only.
- **Rationale**: The spec's acceptance scenarios become the tests.

## D14. Seeds and demo data
- **Decision**: Scripts load landmark candidates from open sources into licence-separated tables (OSM extract, Wikidata, municipal open data, the tourism multilingual database, Wikipedia text with revision), each confirmed by a person before use. A demo script creates one mock account per role and a clearly labelled fictional "Demo Cafe" with its mock walkthrough. Real partner businesses exist only as `draft` places with public facts and no claims. Nothing fabricated is presented as real.
- **Evidence**: research/02 (counts, licences, thin small-business coverage).

## D15. Region configuration
- **Decision**: `regions/nagasaki.json`, validated with Zod at start-up. Adding Malaysia means adding `regions/malaysia.json` and setting that region's keys in the environment. Schema in `contracts/region-config.md`.

## D16. Security baseline
- **Decision**: No server-side fetch of user-supplied URLs in the MVP beyond a fixed allowlist of oEmbed hosts (SSRF guard); Content Security Policy that allows only the embed hosts in use; request validation with Zod; role checks on the server; rate limits on write routes; secrets only in environment variables; audit log for moderation actions and AI edits.

## D17. Hosting region and data residency
- **Decision**: Pin Vercel functions near Tokyo for latency. The Convex region is chosen by the owner when the deployment is created, because it cannot be changed afterwards (moving means export and import). Data residency otherwise stays deferred to the second clarify, and the consent text will name every processor and its region (Convex, Clerk and the AI providers).
- **Evidence** (docs.convex.dev/production/regions): the available regions are `aws-us-east-1`, `aws-eu-west-1` (Ireland), `aws-ap-southeast-2` (Sydney) and `aws-ca-central-1`; there is no Tokyo region. Regions outside the US cost 1.3 times the standard rate.
- **Recommendation**: Sydney, the nearest to Nagasaki. The MVP holds mock and openly licensed data only, so the choice carries no personal-data risk yet, but it should be settled before real owner interviews.
- **Chosen 2026-10-30 (owner)**: Sydney, `aws-ap-southeast-2`. The production deployment `careful-bee-139` was created there (`https://careful-bee-139.ap-southeast-2.convex.cloud`). The dev deployment `brazen-gull-39` is separate and its region was never read. Real owner interviews still wait for the second clarify (data residency, audio retention).
- **Verify (V6)**: Vercel function region and the chosen Convex region against the deferred data-residency decision.
- **Outcome (V6, T122, 2026-10-30)**: Vercel functions are pinned to `hnd1` (Tokyo) by `vercel.json` (`"regions": ["hnd1"]`). The live response header `x-vercel-id: sin1::hnd1::...` from `https://noren.yooi.me/api/geo/search` shows the request entered at the Singapore edge and ran in `hnd1`. The Vercel build machine is in Washington, D.C. (`iad1`); that is where code is compiled, not where requests run. Convex production is Sydney (`aws-ap-southeast-2`, see above). Where data goes, for the consent text (T136): Convex Sydney (stored data), Vercel Tokyo (request handling, no storage of user data), Clerk (sign-in; account-data location still to be read, V1), OpenAI and Anthropic in the US (only text or audio the interviewee has consented to send; regions unverified). The Japanese-resident option for stored data does not exist on Convex (no Tokyo region), so the second clarify must decide whether Sydney is acceptable before real interviews.

## D19. Switch from Neon and Drizzle to Convex (2026-10-29)
- **Why**: The data layer in D3 and D4 (Neon Postgres, Drizzle, Vercel Blob) was my choice at the plan stage, taken because it is the Vercel Marketplace default; the owner never asked for it and uses Convex with Clerk. The owner objected before anything was provisioned, so nothing real was lost.
- **What changes**: Postgres tables, CHECK constraints and plpgsql guard triggers become a Convex schema with validators and `convex-helpers` triggers. The 17 database-rule tests written for PGlite are ported to `convex-test`. Role authority moves from Clerk metadata to the Convex `person` row (D2). Audio moves to Convex storage (D4). Drizzle, drizzle-kit, `@neondatabase/serverless`, `@vercel/blob` and PGlite leave the dependency list; `convex`, `convex-helpers` and `convex-test` join it. The Neon-era draft files were deleted from the project on 2026-10-29 at the owner's instruction.
- **What stays**: Next.js on Vercel, Clerk for accounts, the region config, the domain constants, every spec rule and the constitution. The data model's rules are unchanged; only where they are enforced changes.
- **Where the model changed in the move** (built 2026-10-29 in `convex/`): `sentence_claim` is gone and each page sentence carries `claimIds`, because a join table cannot enforce "at least one citation" at write time and Convex has no commit-time hook; `audit_log.ts` is the row's `_creationTime`; fields are camelCase; `person` is keyed by `tokenIdentifier` (Convex's guidelines say to use it rather than `subject` alone); consent scopes are four `v.literal(true)` fields and the OSM licence is `v.literal("ODbL-1.0")`, so the schema itself refuses the wrong value. Rules that need other rows are triggers (`convex/lib/rules/`), applied through one `mutation` (`convex/lib/gate.ts`) that ESLint makes the only importable one. Limits: triggers see only writes made through that ctx, so the dashboard and `convex import` bypass them; a mutation that catches a rule error could still commit the write, so none may.
- **Deployment** (2026-10-29): Convex project `noren`, team `yf-ooi`, dev deployment `brazen-gull-39`. The region is not printed by the CLI and is still to be read from the dashboard.
- **Development without an account**: Convex runs anonymous local deployments (docs.convex.dev/cli/local-deployments), so the data layer can be built and tested before the owner creates a cloud deployment. The cloud deployment and its region are still an owner action.

## D20. Scope: a public directory of local businesses from open data (owner's rule, 2026-10-30, corrected the same day)
- **Decision**: Noren is about the local places people actually use: bars, restaurants, cafes, retail shops, music shops and artist galleries. It is not about well-known tourist attractions, but nothing is excluded: an attraction may exist as a place, the focus and the default view are the local businesses.
- **Places are public data**: they come from open, crowd-sourced data (OpenStreetMap is the named kind, ODbL with attribution) and from places creators add. A place page is readable by anyone, signed out, with **no owner approval needed to show the place and its public facts**. A steward confirms that a place is real and its facts (names in both languages, a person-placed pin) are right before it goes public (FR-023). Open data stays separate by licence and is credited on the page.
- **The owner's approval remains for the story layer only**: what an owner says in an interview becomes publishable only once the owner confirms it (FR-011), and withdrawing consent hides it (FR-013). Confirmed and published claims are public on the public place page. (The owner's first message said places "further need the approval from the owners"; the correction said no approval is needed because the data is public. This reading keeps approval where the product depends on it: the owner's own words.)
- **Unchanged guards**: no ratings or scores; AI only on consented text; embedded third-party posts keep their consent rule (a steward records the post author's agreement); every page stays hidden from search engines; a private individual's story is consent-first; the launch pack (operator named, takedown contact) is a deliberate switch the owner flips before the URL is shared.
- **Superseded**: the idea of landmark pages as the public demo (spec clarification Q1, User Story 5, SC-009, SC-010, tasks T089 and T090) and the earlier rule that a real business stays a private draft until its owner agrees. Mock content (the labelled Demo Cafe) stays as the walkthrough.
- **Amended 2026-10-31 (owner)**: museums and sights are shown on the map too, each under a category that says what it is (`museum`; `attraction`, "Sight or landmark"), and people filter for themselves. Small places such as a picture book museum are the point; OpenStreetMap cannot tell them from famous ones, so the label and the filter do the work, not a rule that hides them. The map query reads copies of each place's names, pin and published page from the place row, so it is no longer capped at 1,200 places.
- **Dormant, not deleted** (ask before deleting): the landmark/open-text tooling (`convex/openText.ts`, the steward open-text screen, `scripts/seed-landmarks.ts`), and the legacy `landmark` place kind, which grants nothing.
- **Consequences planned** (design in `.scratch/orchestration/plan-public-places.md`): a `public` visibility for confirmed real places, categories with a focus flag, an open-data importer plus a steward candidate screen, attribution on public pages, and the takedown path (US7) before the URL is shared, because every place is now public.
- **Acceptance**: SC-009 and SC-010 are restated once the owner approves the replacement wording.
